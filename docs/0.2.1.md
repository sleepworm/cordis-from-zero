# v0.2.1 — 同 v0.1.1，改用 Cordis

## 需求

和 `v0.1.1` 完全一样：两个问候实现，运行时切换语言。这次用真实的 [`cordis`](https://www.npmjs.com/package/cordis) 包写。

## 代码

`Greeter` 不再是一个普通接口，而是 Cordis 的 `Service` 子类——`super(ctx, 'greeter')` 这一句，就是向 `Context` 注册一个叫 `greeter` 的能力：

```ts
import { Context, Service } from 'cordis'

abstract class Greeter extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')
  }
  abstract greet(name: string): string
}

declare module 'cordis' {
  interface Context {
    greeter: Greeter
  }
}

class EnglishGreeter extends Greeter {
  greet(name: string) {
    return `Hello, ${name}!`
  }
}

class ChineseGreeter extends Greeter {
  greet(name: string) {
    return `你好，${name}！`
  }
}
```

`app()` 只碰 `ctx.greeter`，不 `import` 任何具体的 Greeter 类：

```ts
function app(ctx: Context) {
  console.log('[App]', ctx.greeter.greet('Alex'))
}
```

切换语言不是重新赋值一个变量，而是卸载旧 Plugin、装新 Plugin：

```ts
let greeterFiber = await ctx.plugin(EnglishGreeter)
app(ctx)

await greeterFiber.dispose()
greeterFiber = await ctx.plugin(ChineseGreeter)
app(ctx)
```

## 怎么跑

```bash
npm run demo:cordis
```

## 结果

```
[App] Hello, Alex!
[App] 你好，Alex！
```

和 `v0.1.1` 的输出逐字一致。

## 对照 v0.1.1

两边代码量差不多，`v0.1.1` 里的"一个变量 + 赋值"和这里的"`Service` 类 + `ctx.plugin()`/`dispose()`"比起来，甚至 `v0.1.1` 更短。这不是巧合——`v0.1.1` 本来就是刻意选的、还没有痛点的起点，Cordis 在这一步谈不上有什么优势。真正的对照要等到 `v0.2.2`（日志）和 `v0.2.3`（依赖）：那两步 `v0.1.x` 侧已经写出了明确的胶水代码和风险，`v0.2.x` 侧才有东西可以省。

## 亲手做一个实验：删掉 dispose() 会怎样

把 `await greeterFiber.dispose()` 那一行注释掉，不装载新 Plugin 之前不卸载旧的，直接跑：

```ts
let greeterFiber = await ctx.plugin(EnglishGreeter)
app(ctx)

// await greeterFiber.dispose()
greeterFiber = await ctx.plugin(ChineseGreeter)
app(ctx)
```

```bash
npm run demo:cordis
```

会得到一个真实的报错，而不是静默换成中文：

```
[App] Hello, Alex!
node:internal/process/promises:394
    triggerUncaughtException(err, true /* fromPromise */);
    ^
Error: service "greeter" has been registered at <EnglishGreeter>
    ...
```

**为什么会报这个错**：`Greeter extends Service` 的构造函数里 `super(ctx, 'greeter')` 最终会调用 Context 内部 registry 的 `provide(name, value, check)`（`node_modules/cordis/lib/index.js` 里能直接读到源码）：

```js
provide(name, value, check) {
  return this.ctx.fiber.effect(() => {
    // ...
    if (this.store[key]) {
      throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
    }
    this.store[key] = impl
    // ...
    return async () => {           // 这就是 dispose() 真正执行的清理逻辑
      delete this.store[key]
      // ...
    }
  })
}
```

关键是 `if (this.store[key])` 这一行：**注册前会先检查这个名字是不是已经被占用，占用了就直接 `throw`，不会静默覆盖。** `dispose()` 做的事情，正是调用 `provide()` 返回的那个清理函数，把 `EnglishGreeter` 占用的 `'greeter'` 从 `store` 里删掉。注释掉 `dispose()` 之后，这个名字一直被占着，`ChineseGreeter` 的构造函数走到同一个 `provide()` 时 `this.store[key]` 已经非空，于是直接抛错，`ChineseGreeter` 连注册都没成功。

**和 vanilla 版本的关键差异**：`vanilla/index.ts` 里 `greeter = chineseGreeter` 只是一次变量赋值，没有任何东西检查"这个名字是不是已经被占用"，旧值直接被静默覆盖，不会报错，也看不出你忘了清理旧的。Cordis 这里是主动防御：**同一个能力名字不允许被两份注册同时占用，必须先撤销旧的才能装新的**——这不是 bug，是设计：它把"忘记清理旧实现就直接换新的"这种操作，从"静默出错"变成了"立刻报错"。这个差异会在后面几章反复出现：vanilla 那条线的胶水代码忘了写，通常是悄悄埋下一个 bug；Cordis 这条线忘了该做的清理，往往是当场报错。
