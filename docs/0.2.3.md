# v0.2.3 — 同 v0.1.3，改用 Cordis

## 需求

和 `v0.1.3` 完全一样：问候语要跟着"现在几点"变，而 `Clock` 本身可能还没准备好、可能会消失、可能会恢复。

## 代码

`Clock` 是个普通 `Service`，和 `Greeter` 结构一样，自己完全不知道谁依赖它：

```ts
class Clock extends Service {
  constructor(ctx: Context, public period: Period = 'morning') {
    super(ctx, 'clock')
  }
  setPeriod(period: Period) {
    this.period = period
  }
}
```

`Greeter` 依赖 `clock`，只需要声明一行：

```ts
abstract class Greeter extends Service {
  static inject = ['clock']
  constructor(ctx: Context) {
    super(ctx, 'greeter')
  }
  abstract greet(name: string): string
}
```

`EnglishGreeter`/`ChineseGreeter` 通过 `this.ctx.clock.period` 读取当前时段：

```ts
class EnglishGreeter extends Greeter {
  greet(name: string) {
    return `${englishText(this.ctx.clock.period)}, ${name}!`
  }
}
```

`app()` 里重新出现了 `if (!ctx.greeter)`——这一点和 `v0.1.3` 一致，Cordis 不会替我们消灭"能力可能不存在"这个问题：

```ts
function app(ctx: Context) {
  if (!ctx.greeter) {
    console.log('[App] ctx.greeter is unavailable, skip greeting')
    return
  }
  console.log('[App]', ctx.greeter.greet('Alex'))
  ctx.emit('greet', 'Alex')
}
```

## 怎么跑

```bash
npm run demo:cordis
```

## 结果

```
[App] ctx.greeter is unavailable, skip greeting
[App] Good morning, Alex!
[LOG] greeted Alex
[App] 早上好，Alex！
[LOG] greeted Alex
[App] ctx.greeter is unavailable, skip greeting
[App] 晚上好，Alex！
[LOG] greeted Alex
```

和 `v0.1.3` 的现象逐条一致：`Clock` 未加载时 `Greeter` 不可用；`Clock` 加载后自动可用；换语言不受影响；`Clock` 卸载后自动跟着不可用；重新加载（带新时段）后自动恢复，且读到新值。

## 对照 v0.1.3

`v0.1.3` 里为了让 `greeter` 跟 `clock` 的存在与否保持同步，手写了一个 `refreshGreeter()` 函数，而且**必须在每一个碰到 `clock` 生命周期的地方手动调用它**——这正是那一章暴露的问题：忘记调用，`greeter` 就会悄悄停在过期状态。

这里的 `main()` 里，从加载 `Clock` 到卸载 `Clock` 再到带新参数重新加载，**没有一行代码对应 `refreshGreeter()`**。`static inject = ['clock']` 这一行声明，替代了 `v0.1.3` 整段"手动同步"胶水代码：

- `Clock` 未就绪时，`Greeter` 的构造函数根本不会执行——不是构造完了才手动检查，而是从一开始就不启动。
- `Clock` 卸载时，`Greeter` 自动跟着失效——不需要任何监听/通知代码。
- `Clock` 恢复时，`Greeter` 自动重新构造——走的是和"第一次就绪"完全相同的机制，不是两套逻辑。

这是全篇第一次看到 Cordis 真正省下了"依赖管理"这类结构性的胶水代码，而不只是省掉几行退订逻辑。
